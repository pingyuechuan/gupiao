## 1. RFC — Request for Change

### 1.1 为什么必须做这个变更

当前 Phoenix Beta 0.7 的真实状态（已逐文件核对，非推测）：

| 事实 | 证据 | 后果 |
|---|---|---|
| **项目不在版本控制下** | `git rev-parse` 返回「NOT a git repo」 | **没有任何回滚能力**。改坏了只能靠记忆恢复 |
| **8 条行情代理只存在于 dev server** | `vite.config.ts:37-87`，`server.proxy` 段 | 静态部署后 `/em` `/ths` `/tc` `/sina` `/tk` `/sk` `/emh` `/ems` **全部 404** |
| 6 个数据层文件硬编码相对路径 | `batchQuote.ts` `klineSources.ts` + 4 个 Provider | 前端无法指向外部网关 |
| 包名/版本与产品名不一致 | `package.json` = `a-share-ai-coach@2.0.0` | 对外身份混乱 |

> **一句话结论：现在把 `dist/` 传到任何静态托管，陌生用户拿到的是一个「界面完整、数据全空」的壳子。**
> AIMS 五维评分、记忆、准确率——一条数据都跑不出来。

Beta 阶段的唯一目标是「找到真正用户」。在上述状态下，**这个目标的完成度是 0%**。
0.8 不增加任何功能，只解决一件事：**让产品从「本机 demo」变成「互联网上可访问的服务」**。

### 1.2 变更类型

- [x] 基础设施（Infrastructure）
- [x] 架构变更（数据层 URL 抽象）
- [ ] 新功能
- [ ] UI / 交互变更
- [ ] AIMS 算法变更

### 1.3 五问评审

| # | 问题 | 答 | 说明 |
|---|---|---|---|
| 1 | 用户真的需要吗？ | ✅ 是 | 不上线，用户连"需要"的机会都没有 |
| 2 | 用户每天会打开吗？ | ✅ 是 | 这是"能否打开"的前提条件 |
| 3 | 能提高留存吗？ | ✅ 是 | 留存的分母来自这里 |
| 4 | 能形成竞争优势吗？ | ⚪ 中性 | 部署本身不是壁垒，但是壁垒生效的载体 |
| 5 | 以后容易维护吗？ | ✅ 是 | 一次投入，长期复用；且首次建立回滚能力 |

**0 个否 → 通过。**

## 4. Risk Assessment — 风险评估

### 🔴 R1（P0，架构级不确定性）海外服务器访问国内行情源

**风险**：Railway 与 Vercel 的机房都在境外。同花顺 `d.10jqka.com.cn`、东财 `push2.eastmoney.com`、腾讯 `qt.gtimg.cn`、新浪 `hq.sinajs.cn` 这类国内公开行情接口，**对境外 IP 常见的行为是：限流、超时、返回空数据，或直接拒绝**。

**影响**：如果成立，整个 0.8 的技术方案作废 —— 部署成功了，数据依然是空的，等于换了个地方展示空壳。

**这是 0.8 唯一的架构级未知，必须最先消除。**

**缓解措施**：
1. **Day-1 强制 Spike**：先在 Railway 上跑一个只有 8 个 GET 的最小探针，实测 4 个上游的成功率与 P95 延迟。**Spike 不通过，立即暂停 0.8 并重新评估架构**，不允许带着这个未知往下做。
2. 备选方案 B：Railway 选择亚太区域（新加坡 / 东京），延迟与可达性显著优于美西。
3. 备选方案 C：网关部署到国内云厂商（腾讯云 / 阿里云轻量），前端仍在 Vercel。代价是引入备案。
4. 备选方案 D：网关侧加 30–60s 结果缓存，用低频真实请求换稳定性。

> **我建议把 Spike 结果作为 0.8 正式开工的前置门禁。**

### 🔴 R2（P0，用户可达性）Vercel 在中国大陆访问不稳定

**风险**：目标用户是 **A 股散户，几乎 100% 在中国大陆**。而 `*.vercel.app` 域名在国内解析与访问长期不稳定；即使绑定自定义域名，Vercel 的 CDN 在国内的可达性与速度**不可控**。

**影响**：Beta 用户打开白屏或极慢 → 直接判定产品"坏了" → 招募到的第一批种子用户全部流失。**这比功能缺失更致命。**

**缓解措施**：
1. 与 R1 的 Spike 合并：用真实国内网络环境实测首屏可达性与加载耗时。
2. 备选：Cloudflare Pages（国内可达性一般优于 Vercel）。
3. 备选：国内静态托管 + 备案（可达性最优，代价是 15–20 工作日的备案周期）。
4. **最小验证策略**：先用 Vercel 上线，向 5–10 名真实用户做可达性抽样，再决定是否迁移。

### 🟠 R3（P1，目标冲突）「登录认证」与「让真实用户能访问」相互矛盾

**风险**：0.8 的唯一目标是"让真实用户能够访问并开始测试"。而登录/注册是**转化漏斗上最大的一道摩擦**，会在用户看到任何产品价值之前就流失一批。

我在 `02_Roadmap §4.1` 曾用五问否决账号体系（5 个否）。PO 本次将「登录认证」列入 0.8，我理解真实诉求可能不是"账号"，而是 **"Beta 阶段需要门禁，不想让产品公开裸奔"**。

**缓解措施**：提供三个方案供裁决，见 §7 决策 D2。我的推荐是**邀请码门禁**——满足门禁诉求，零注册摩擦，且不引入隐私合规负担。

### 🟠 R4（P1，无回滚基线）项目当前不在版本控制下

**风险**：现在做任何改动都无法回退。

**缓解措施**：S1 置于最高优先级，先打 `v0.7.0` tag 建立锚点，之后才允许动代码。

### 🟠 R5（P1，成本）Railway 已无免费层

**风险**：Railway Hobby 计划约 **$5/月起**，按用量计费。Supabase 免费层在无活动时会**暂停项目**。Beta 期用户量小、访问不连续，容易触发休眠。

**缓解措施**：0.8 上线后监控实际用量；若 Railway 成本不可接受，网关可平移至 Cloudflare Workers（免费额度充足，且国内可达性更好）。**架构上保证网关是无状态的，迁移成本 <1 天。**

### 🟠 R6（P1，合规）域名备案与投资建议内容合规

**风险**：
1. 未备案域名向中国大陆提供服务存在合规风险；若走国内节点，备案是硬前置（15–20 工作日）。
2. 产品输出"建议仓位""可以买指数"等内容，**必须有醒目免责声明**，否则涉及无牌照投资顾问风险。

**缓解措施**：S9 的 Beta Banner 强制包含免责声明并要求用户确认；域名策略由 PO 在 D1 裁决。

### 🟡 R7（P2，安全）密钥泄漏

**风险**：Supabase service_role key 若进前端 = 数据库全裸。

**缓解措施**：前端只用 anon key；所有密钥走平台环境变量，**禁止提交进 git**（`.gitignore` 已覆盖 `.env.local`，需再确认 `.env` 也被忽略）。

### 🟡 R8（P2，回归）数据层 6 个文件路径改造

**风险**：路径拼接改错导致 dev 环境也拉不到数据。

**缓解措施**：`VITE_API_BASE` 默认空字符串 → dev 行为逐字节不变；改造后跑一次现有 Playwright 冒烟测试比对。

## 5. Rollback Plan — 回滚方案

### 5.1 分层回滚能力

| 层 | 回滚手段 | 耗时 | 数据损失 |
|---|---|---|---|
| 前端 | Vercel Dashboard → 上一个 Deployment → Promote to Production | **< 1 分钟** | 无 |
| 网关 | Railway → Deployments → Redeploy 上一版本 | **< 2 分钟** | 无 |
| 代码 | `git revert <sha>` 或 `git reset --hard v0.7.0` | < 1 分钟 | 无 |
| 域名 | DNS 切回旧记录 / 摘除 CNAME | 5–30 分钟（TTL） | 无 |
| 数据库 | 0.8 **不建业务表、不写数据** → **无需回滚** | — | 无 |

> 0.8 刻意设计为"**无数据写入**"版本，这让回滚变成纯粹的部署回退，风险极低。

### 5.2 完全放弃（Kill Switch）

若 0.8 上线后发现致命问题（如 R1/R2 成立）：

1. **前端**：Vercel Promote 回 0.7 构建产物 —— 但 0.7 无网关，等价于下线。
2. **推荐做法**：网关侧下发降级标志，前端显示「Beta 维护中，稍后回来」，而不是白屏。
   → 需在 S8 的 `/healthz` 中预留 `maintenance: boolean` 字段（**成本 <10 行，强烈建议纳入 0.8**）。
3. **最终兜底**：摘除域名解析，回到本机开发状态。产品数据全在用户 localStorage，**不会有任何用户数据丢失**。

### 5.3 回滚触发条件（任一命中即回滚）

- 首页在真实国内网络下 **5 秒内无法出现行情数据**
- 网关上游成功率 **< 80%**
- 出现任何 P0 级崩溃（白屏 / 无限 loading）
- 单日成本异常超出预算

### 🔺 D2 · 登录认证的具体形态

我需要确认：这一项的真实诉求是 **「控制 Beta 参与者」** 还是 **「建立用户账号体系」**？

| 选项 | 形态 | 摩擦 | 工期 | 合规负担 |
|---|---|---|---|---|
| **A** | Supabase Auth 邮箱 Magic Link（免密） | 中（需收邮件） | 2 天 | 中（存邮箱=个人信息） |
| **B（我推荐）** | **Beta 邀请码门禁**：输入码即进入，存 localStorage，无账号 | **极低** | 0.5 天 | 无 |
| **C** | 完整邮箱+密码注册 | 高 | 3 天 | 高（密码找回、隐私） |

**我的建议：选 B。** 理由：
1. 0.8 的唯一目标是「让真实用户能访问」，**每加一道注册就少一批用户**；

4. 0.5 天 vs 3 天，省下的时间够把 R1 的架构风险彻底消灭。

若 PO 判断"必须有真实账号才能沉淀用户资产"，我选 **A**（无密码，避免找回流程）。
